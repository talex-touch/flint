# Method

Flint is a decision model: it answers questions with typed options and
calibrated probabilities instead of generating text. This document describes the
architecture it trains a head on, where that architecture comes from, and which
parts of the design are load-bearing for the properties the rest of the
repository depends on.

**The architecture is not ours.** Flint trains and serves a head on top of
`laya` — a public Apache-2.0 "System 1 decision engine" by Convai Innovations
([package](https://github.com/NandhaKishorM/laya),
[weights](https://huggingface.co/convaiinnovations/laya)) — and every call into
it goes through `flint/engine.py`. What this repository owns is the recipe, the
evaluation protocol and the checkpoints; §7 says which of the ideas below are
borrowed.

## 1. Non-autoregressive by construction

A chat model produces a string one token at a time, each conditioned on the last.
Flint produces a distribution over a closed set of options in **one forward pass**,
with no decoding loop and no output tokens.

The difference is not an optimisation, it is what makes the other properties
possible:

- **No hallucination is representable.** The output is a softmax over the markers
  that were placed in the input. There is no mechanism by which an option that
  was not offered can be returned.
- **Cost is one pass, not per token.** Latency does not grow with the length of
  the answer, because there is no answer text.
- **Options are compared, not generated in sequence.** Position in the list is a
  layout detail rather than a prefix, which is what makes the permutation
  invariance in §5 meaningful.

## 2. One sequence per question

Each question is packed into its own sequence:

```
[CLS] <type> instructions [SEP] [MASK] option_0 [MASK] option_1 … [SEP] state [SEP]
                                 ↑ marker positions, one per option
```

The state is repeated in every question's sequence. That is deliberate: questions
that share a `state` cannot see each other. A question about one part of a form
cannot be influenced by what another question in the same request asked, which
matters when the requests are generated by a caller that may ask several
independent things at once.

The option markers are read by a small transformer head, then a scorer produces
one logit per marker, and a softmax over the markers gives the distribution. A
question type embedding is added to every position before the head, so the three
question types (choice, yes/no, rating) share one encoder's representations while
still being told apart. A second head scores a coarse "act or escalate" decision
from the pooled state and four summary features of the distribution.

This is the upstream design; `flint/engine.py` is a thin adapter to it and does
not reimplement any of it.

## 3. The objective is a proper scoring rule

Training minimises the **log score** against a target distribution over the
options — that is, cross-entropy where the target need not be one-hot.

The relevant property is that the log score is *proper*: its expectation is
minimised by reporting the true distribution and not by reporting a sharper or
flatter one. This is what makes the output usable as a probability rather than as
a ranking that happens to be normalised. A model trained to minimise a proper
score has a reason to say 0.6 when it is right six times in ten; under a
classification loss with hard labels it has no such reason, and in practice it
does not.

The engine also exposes a variant that combines the spherical score and the
ranked probability score (`laya.common.proper_reward`), both proper as well.
Flint uses the log score because its gradient decomposes per row, which makes the
effect of label smoothing and of soft targets possible to reason about; the choice
is a convenience, not a claim that it is better.

Label smoothing mixes a uniform component into every target. It is not cosmetic:
hard targets instruct the model to be certain, and certainty on a genuinely
ambiguous item is the failure the calibration sections below are about.

## 4. Confidence is normalised entropy

The engine reports confidence as `1 - H(p) / log k`, where `k` is the number of
options for that question. This is not the top probability, and the difference is
load-bearing — `docs/api.md` works through it. Two consequences shape everything
downstream:

1. **A confidence threshold is not comparable across option counts.** A gate
   fitted on three-option questions is a different gate at thirty, which is why
   evaluation reports `byWidth`.
2. **A temperature is an operating point, not a calibration constant.** Because
   the normalisation is by `log k` and the rows have different `k` and different
   peakedness, a temperature moves rows against each other in confidence order.
   It never changes the argmax, so accuracy is untouched, but the set of answers a
   fixed threshold releases changes — measurably, by a lot
   (`docs/evaluation.md` §3).

Calibration itself is measured with the expected calibration error over
confidence bins, computed both on the top probability and on the entropy
confidence, because they can disagree and it is not obvious in advance which one
a given checkpoint gets wrong.

## 5. Selection, and treating a choice as a preference

A choice question is a set of options and one of them is right. The softmax over
option scores is exactly a conditional-logit model — the form Bradley & Terry
introduced for paired comparisons, extended to a full ranking. Reading it that
way is what makes the design choices fall out rather than being arbitrary:

- **Option order should carry no information.** A conditional logit is invariant
  to the order of the alternatives. Training permutes the options of choice
  questions, remapping the target so the question is unchanged, and the same
  idea reappears as a measurement: `flint.evaluate` reports how often the chosen
  *option* changes when the layout does. It compares identities, not positions.
- **A "none" option is a real alternative.** Declining is a decision. A model
  whose only alternatives are the things it was shown has no way to say that
  none of them fits, and that is frequently the correct answer.
- **Width matters.** A four-way choice and a forty-way choice are different
  problems, and the effects above compound with width.

Ratings are handled as a choice over an ordered scale, and yes/no questions as a
two-alternative case with a distinct head — same machinery, different target
semantics.

## 6. Knowing when not to answer

The gate in front of the model is the classical **reject option**: a classifier
that may decline is allowed to trade coverage against error, and Chow derived the
optimal rule for the two-class case. Everything in `flint/metrics.py` about
coverage at a fixed error budget is that idea applied to a k-way decision with a
calibrated score rather than a two-class posterior.

Selective classification generalised it to deep networks: with a fixed model and a
fixed budget, the optimal accepted set is a threshold on a confidence score, and
the interesting quantity is the risk–coverage curve rather than a single number.
That is why `docs/evaluation.md` insists on comparing two checkpoints at matched
coverage instead of at one threshold: a single point on that curve is a statement
about the threshold, not about the model.

Conformal prediction is the distribution-free alternative — it converts a score
into a set with a coverage guarantee under exchangeability. Flint does not use it,
and the reason is worth stating rather than leaving as an omission: the guarantee
is marginal over a calibration set, and the product wants per-decision control
("did this question have enough options to be decidable"), which is a different
promise. It is the right tool if a coverage guarantee is what you need.

## 7. What is borrowed, and what that means for this repository

| idea | where it comes from | used for |
| --- | --- | --- |
| non-autoregressive decision engine, per-type head | `laya` (Apache-2.0), Convai Innovations — its **`multilingual`** checkpoint is the base every Flint weight comes down from | the architecture, imported rather than copied |
| conditional-logit / paired-comparison form | Bradley & Terry (1952) | why option order is permutation-invariant |
| proper scoring rules | the log score; the engine's spherical + ranked-probability variant | the training objective |
| label smoothing | standard | keeping the target from demanding certainty |
| knowledge distillation | Hinton et al. (2015); Sanh et al. (2019) | soft targets, when a record carries a distribution |
| parameter-efficient fine-tuning | Houlsby et al. (2019); Hu et al. (2022) | why a small head over a frozen or lightly-tuned encoder is enough |
| reject option | Chow (1970) | the coverage/error trade-off |
| risk–coverage analysis | El-Yaniv & Wiener (2010); Geifman & El-Yaniv (2017) | how checkpoints are compared |
| calibration and ECE | Guo et al. (2017) | measuring whether confidence is honest |
| models reporting their own uncertainty | Kadavath et al. (2022) | the abstention axis |
| distribution-free uncertainty sets | Angelopoulos & Bates (2021) | considered and not used; see §6 |

Two notes on this list, because a reference list is easy to fill dishonestly:

- **Nothing here is claimed as our contribution**, and nothing here is copied.
  The architecture is imported from a public package under its own licence, and
  the rest are ideas, which are reusable in the way weights are not.
- **Every entry was checked against a first-party source** (IEEE Xplore, PMLR,
  JMLR, ICLR, NeurIPS, Biometrika via Crossref, arXiv) on 2026-09-25. Where a
  venue could not be confirmed from a first-party page, the citation says
  *preprint* rather than the venue it is usually quoted with. One frequently
  cited paper on permutation rankings was **dropped** rather than listed: the
  first-party page could not be read, and a DOI that appeared to be it resolved
  to an unrelated article. A reference that has not been opened is a rumour with
  a year attached.
